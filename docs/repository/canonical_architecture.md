# Canonical repository architecture

## Purpose

This document defines the target maintained architecture for Lamb Fundamental Solver after issue #139. It is an ownership contract, not a scientific redesign.

The repository exists primarily to provide:

1. canonical forward Lamb-wave dispersion solvers;
2. canonical inverse fitting of those solvers to experimental dispersion data.

Other capabilities exist only in support of those two goals.

## Target repository shape

```text
Lamb-fundamental-solver/
  src/
    +lamb/
      +models/
        +rayleigh_lamb/
        +mrlfe/
        +acoustoelastic_iop_hgo/
      +fitting/
      +elasticity/
      +grids/
      +sweeps/              optional minimal generic engine only

  app/
    solver/

  studies/

```

Directories are created only when a real maintained responsibility exists. The final tree must not contain empty folders for symmetry.

## Ownership definitions

### `src/+lamb/+models/`

Owns complete forward physical models and their scientific/numerical implementation.

The three canonical families are Rayleigh-Lamb, mRLFE, and acoustoelastic IOP/HGO. Each family may retain the established responsibility spine when applicable:

```text
configuration  request validation, defaults, requested/effective resolution
core           model-owned physical/problem construction
equations      model equations when a distinct owner is justified
constitutive   constitutive mechanics when a distinct owner is justified
solvers        orchestration of one maintained solve
tracking       candidate/branch continuation and refinement
policies       genuine scientific selection/termination policy
quality        assessment of already selected official output
results        construction of canonical public results
```

Model families do not need identical internal folders when the physics does not require them.

### `src/+lamb/+fitting/`

Owns inverse dispersion fitting.

Canonical conceptual route:

```text
family fit API
  -> family fit-problem construction
  -> shared fitting/optimization primitives
  -> family model evaluator
  -> canonical forward model API
```

Fitting does not own forward equations, tracking, or alternate solver implementations. Shared fitting metrics, residual handling, sensitivity, and identifiability belong here when genuinely model-neutral.

### `src/+lamb/+elasticity/`

Owns neutral reusable elastic-property relations and conversions such as isotropic transformations between shear modulus, Poisson ratio, Young's modulus, Lamé parameters, and derived wave speeds.

It is not a model family.

### `src/+lamb/+grids/`

Owns neutral construction of frequency/discretization vectors used across families or surfaces.

A grid builder must not remain under one model family merely because it originated there.

### `src/+lamb/+sweeps/`

Sweep is secondary infrastructure, not a primary scientific capability.

This package survives only if a small generic iteration engine materially reduces duplication. It may apply parameter values, call an evaluator, collect canonical results, and record operational status/timing.

It must not own:

- model physics;
- model-specific scientific policy;
- plotting or persistence;
- GUI state;
- sensitivity-study interpretation.

If the generic engine ceases to justify an independent package, it may be eliminated.

## Human-facing application

### `app/solver/`

Owns the main solver GUI surface and translation between UI state and canonical model APIs.

### `app/fitting/`

Owns the fitting GUI surface and translation between experimental/UI state and canonical fitting APIs.

### `app/execution_profiles/`

Owns human-facing Fast/Balanced/Robust profile translation where the profile is a surface-level request for numerical effort. Profiles must not redefine physical meaning.

### `app/utilities/`

Contains only small, genuinely app-specific helpers. It must not become a replacement for `shared/`.

The target architecture does not include a SweepTool GUI unless a concrete product requirement is established.

## Studies

### `studies/sensitivity/`

Owns reproducible parameter-sensitivity campaigns and scientific figures generated by repeated calls to canonical solvers.

Examples include variation of thickness, stiffness, viscosity, IOP, or constitutive parameters. These studies may configure parameter sets, call maintained APIs, summarize results, plot figures, and save study outputs.

They must not reproduce solver implementation.

### `studies/solver_diagnostics/`

Owns reproducible investigations used to understand or characterize solver behavior, for example:

- branch-family inspection;
- modal-atlas inspection;
- grid/start-frequency sensitivity;
- branch/tracking reliability;
- numerical failure characterization.

A solver diagnostic may inspect production evidence but must not maintain a second implementation of production candidate discovery, branch linking, tracking, or scientific policy.

Useful stable reliability metadata that belongs to every normal solve remains under the corresponding model `quality`/result contract rather than in studies.

## Directories to retire

### `analysis/`

Retire completely. Its current responsibilities are redistributed to fitting, sweeps, studies, model quality, IO/persistence owners, or app presentation as appropriate. `analysis` must not remain as a catch-all category.

### `examples/`

Current sensitivity and diagnostic scripts are not true examples and should move to `studies/`.

After migration, remove `examples/` unless a deliberately small set of short API demonstrations provides unique value beyond README/model documentation.

### generic `shared/`

Retire generic shared ownership. A reusable function must have a semantic owner (`elasticity`, `grids`, `fitting`, a specific model, app utilities, etc.).

### migration-era naming

Final canonical code/documentation should not use names such as `active`, `current`, `final`, `new`, `v2`, `candidate`, `legacy`, or `experimental` merely to describe chronology. Validated current implementation is simply the canonical implementation.

Names representing a real runtime or scientific distinction are allowed.

## IO and plotting

Do not create top-level `+io` or `+plotting` packages automatically.

During migration classify each existing function by real ownership:

- persistence used only by a sensitivity/diagnostic study -> study-local owner;
- rendering used only by app -> app owner;
- rendering used only by studies -> study owner;
- truly reusable maintained persistence/rendering across independent callers -> introduce a narrowly defined package only after evidence of shared responsibility.

This avoids recreating a generic utility layer under a different name.

## Canonical scientific contracts

The existing approved contracts remain authoritative during migration.

### Official curve

```text
frequency_Hz       N-by-1
phaseVelocity_mps  N-by-1
wavenumber_radpm   N-by-1
validMask          N-by-1 logical
```

Invalid official phase velocity is `NaN` and `validMask = false`.

### Quality

```text
pointCount
validCount
validFraction
accepted
reason
```

Quality assesses an already selected official result. It does not select, reconnect, smooth, or replace the branch.

### Configuration

```text
configuration.requested.parameters
configuration.requested.options
configuration.effective.parameters
configuration.effective.options
```

### Execution

```text
engine
elapsedSeconds
```

Model-specific evidence is allowed below explicit metadata/debug boundaries without destabilizing the public spine.

## Canonical numerical implementation

The following are established production behavior and must survive structural migration:

### AE IOP/HGO

- current atlas-based A0 solution strategy;
- Cp-dependent state precomputation/caching;
- current candidate discovery and branch-linking semantics;
- current A0 selection policy;
- bounded continuous refinement after branch selection;
- current quality/result contracts.

### mRLFE

- optimized coarse candidate discovery;
- dense rescue used only where currently required;
- selected-candidate bounded/continuous refinement;
- current branch policies and physical-tail termination behavior;
- established fitting performance optimizations/caching;
- no plotting-time smoothing of scientific curves.

### Rayleigh-Lamb

- canonical A0/S0 solve behavior and analytical approximation responsibilities;
- current public result contracts.

The intentional scientific cross-family dependency remains only where mRLFE uses Rayleigh-Lamb as its physical seed/reference. Neutral utilities such as frequency-grid construction must not create cross-family dependencies.

## Tests

Tests should eventually mirror responsibility rather than implementation history:

```text
tests/models/
tests/fitting/
tests/sweeps/            if the generic sweep engine remains
tests/app/
tests/studies/           only when study-level contracts warrant automation
tests/repository/
tests/runners/
tests/tooling/
```

The six canonical runners remain the maintained validation surface unless explicitly redesigned after the migration.

Structural migration must preserve the validated scientific/numerical baseline. Do not update golden values or tolerances to hide refactor drift.

## Documentation after migration

Permanent documentation should explain the system that exists now, not preserve the chronology of the restructuring campaign.

At the end of issue #139:

1. preserve scientific/model documentation and durable architectural conventions;
2. consolidate overlapping repository policies/contracts;
3. remove obsolete planning, readiness audits, campaign handoffs, superseded architecture descriptions, and historical status documents whose unique information is already preserved by code/Git/PR history;
4. remove transition-era words from canonical names;
5. keep `AGENTS.md` short enough to serve as the first context map for implementation agents.

## Migration acceptance

The migration is complete only when:

1. every maintained responsibility has one obvious semantic owner;
2. `analysis/` and unjustified generic shared ownership are gone;
3. solver and fitting remain the clear primary capabilities;
4. sensitivity and solver investigations are visibly secondary studies;
5. no alternate scientific pipeline or compatibility layer was introduced;
6. approved numerical optimizations and scientific behavior are preserved;
7. documentation describes the canonical state rather than the migration history;
8. all six canonical runners pass (115-test baseline unless intentionally changed by reviewed test-structure work);
9. representative performance checks show no material structural-regression slowdown;
10. `main` is updated only after explicit user authorization.
